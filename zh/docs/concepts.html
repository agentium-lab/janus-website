核心概念

Janus 是一个持久化 Agent 任务代理（Broker）。它位于 Agent 之间，以治理、路由和可观测性保障任务的可靠交付。

任务（Task）

工作的基本单位。任务携带一个不透明载荷（信封 envelope），从源 Agent 发往目标消费者。每个任务都有唯一 ID、租户作用域，以及完整的生命周期状态：

pending → claimed → in_progress → completed
                                        → failed
                                        → nacked → pending (重试)
                                                  → dlq

邮箱（Mailbox）

一个命名队列，任务在此投递。Agent 从自己拥有的邮箱拉取任务。邮箱是持久的——即使 Agent 崩溃，任务也会保留，直到 Agent 恢复并拉取它们。

关键属性：

  • 作用域限定在某个租户内
  • 由一个或多个 Agent 拥有（agent_id）
  • 任务按优先级顺序 FIFO 拉取

租约（Lease）

Agent 拉取任务时，会获得一个限时租约。租约防止其他 Agent 抢占同一任务。如果 Agent 未确认（ACK）就崩溃：

  • 租约在配置的超时时间后过期
  • 任务回到 pending 状态，可被其他 Agent 重新拉取
  • 幂等的 ACK/NACK 确保精确一次（exactly-once）语义

信封（Envelope）

载荷包装器。包含：

  • type — 消息类型标识
  • payload — 实际数据（结构化 JSON）
  • priority — high / normal / low
  • context_refs — 对共享工件的引用（文件、图片、先前结果）

路由与能力解析

Janus 支持两种派发模式：

  • 直接路由 — 发布到指定邮箱
  • 基于能力 — 描述你的需求，Janus 自动找到最合适的 Agent

意图解析器（Intent Resolver）接受自然语言描述，并将其匹配到已注册的 Agent 能力：

client.resolve_intent("Review a Go pull request for race conditions")
# → Confidence: 0.92
# → Matched capability: "go-code-review"
# → Suggested target: "review-mb"

治理（Governance）

每一次任务派发都会经过策略与预算检查：

  • 策略引擎 — 谁能调用谁、使用什么数据形态
  • 预算控制 — RPM / TPM / 并发 / 每日成本限制
  • 审计轨迹 — 每一次 publish、pull、start、ack、nack 都被记录
  • 人工审批 — 高风险任务可以要求手动审批

协议网关（Protocol Gateways）

Janus 原生支持多种 Agent 通信协议：

  • A2A 网关 — Google Agent-to-Agent 协议（Agent Card、Task Send）
  • ACP 网关 — Anthropic Communication Protocol（Manifest、Runs）
  • MCP 网关 — Model Context Protocol（Tools、Resources）
  • REST API + gRPC — 面向 SDK 客户端的原生 Janus API

持久化模型（Durability Model）

任务被双写至 PostgreSQL（真相源）与 NATS JetStream（快速投递）。如果 Broker 进程中途崩溃：

  • 已认领但未 ACK 的在途任务，其租约会过期
  • outbox 机制确保 Broker 崩溃期间不会丢失任何任务
  • 可通过 CLI 从死信队列手动重放

租户隔离（Tenant Isolation）

每个任务、邮箱和工件都限定在租户内。跨租户访问会被自动拒绝。所有审计事件都带有租户 ID 标签。

Janus 使用双写持久化（PG + NATS）保障可靠性。Broker 能在 Agent 崩溃、网络分区乃至自身重启的情况下不丢失任何任务。
