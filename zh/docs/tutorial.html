完整示例：智能客服中心

流程模式示意——片段演示流程。前置条件（在快速开始中一次性完成）：导出 JANUS_API_KEY；创建客户端——from janus_broker import AckRequest, JanusClient 后 client = JanusClient("http://localhost:8080", tenant_id="acme", api_key=os.environ["JANUS_API_KEY"])——并注册所示 Agent/邮箱（reviewer/logistics-bot/shipping-bot/return-bot/notify-bot 与各自的 review-mb/logistics-mb/shipping-mb/return-mb/notify-mb 邮箱及能力）。生产中请把拉取包进 JanusWorker 循环。

本节通过一个真实的多 Agent 协作场景——处理客户发错货投诉——展示 Janus 的路由、可靠性和治理功能如何在一个类生产工作流中协同工作。

你将学到

  • 使用 target_type: intent 进行 LLM 驱动的自然语言路由
  • 基于能力的路由（target_type: capability）
  • 并行任务扇出与 Barrier 同步
  • 任务租约过期与自动恢复（Agent 崩溃场景）
  • Agent 之间的数据传递（A 的产出 → B 的输入）

场景

客户投诉："我订购了红色手机，却收到了蓝色的。需要换货。"

Janus 协调四个 Agent来处理：

  1. 物流员 — 调查原始订单（能力：wrong_item_investigate，团队：logistics）
  2. 发货员 — 发出正确的红色手机（能力：reship，团队：warehouse）
  3. 回收员 — 安排取回错误的蓝色手机（能力：retrieve_wrong，团队：warehouse）
  4. 通知员 — 向客户发送状态更新（能力：notify，团队：support）

流程（含故障注入）

客户："订的红色收到了蓝色"
    │
    ▼  intent LLM → "wrong_item_investigate"
    │
物流员 ─── 拉取订单 ─── 💀 崩溃(不 ACK) ─── 租约过期 ─── 恢复 ─── ACK
    │
    │  数据：{order: "ORD-789", ordered: "red", shipped: "blue"}
    ▼
    ├── ► 发货员 ─── 发正确的红色 ─── ACK {tracking: "SF789"}
    ├── ► 回收员 ─── 取回错误的蓝色 ─── ACK {pickup: "PU123"}
    └── ► 通知员 ─── "换货已启动" ─── ACK
            │
            ▼
         通知员 ─── "红色已发SF789，蓝色取件PU123" ─── ACK

核心设计：物流员的调查结果（哪个商品正确、哪个错误）驱动下游 Agent 的行为——发货员读取调查数据知道发什么；回收员读取调查数据知道回收什么。Agent 之间不是各干各的，而是通过数据流协作。

第 1 步：注册 Agent 及其能力

每个 Agent 声明自己能做什么（capability）和所属团队（team）。Janus 用能力做匹配，用团队做分组路由。

# 注册四个 Agent
for agent in [
  {"id": "logistics-bot", "display_name": "物流员", "team": "logistics"},
  {"id": "shipping-bot", "display_name": "发货员", "team": "warehouse"},
  {"id": "return-bot", "display_name": "回收员", "team": "warehouse"},
  {"id": "notify-bot", "display_name": "通知员", "team": "support"}
]:
    client.create_agent(agent["id"], agent["display_name"], agent["team"])

然后为每个 Agent 分配能力和创建邮箱（任务队列）：

# 能力：每个 Agent 能做什么
caps = {
  "logistics-bot": "wrong_item_investigate",
  "shipping-bot":  "reship",
  "return-bot":    "retrieve_wrong",
  "notify-bot":    "notify",
}
# 创建邮箱（物流邮箱 ACK 超时设为 5 秒，用于租约过期测试）
client.create_mailbox("logistics-mb", "logistics-bot", ack_wait=5)
client.create_mailbox("shipping-mb", "shipping-bot")
client.create_mailbox("return-mb", "return-bot")
client.create_mailbox("notify-mb", "notify-bot")

第 2 步：用意图路由（LLM 驱动）发起任务

不指定具体的 agent 或能力，而是用 target_type: intent 配合自然语言描述。Janus 的 LLM 解析器将请求映射到最匹配的能力：

# logistics-bot 拉取任务...
result = client.pull_task("logistics-mb", "logistics-bot")

# 模拟崩溃——不 ACK，直接停止。
# 租约过期后（本配置为 5 秒），
# Janus 自动把任务重新投递回邮箱。

# Agent 恢复后再次拉取：
result = client.pull_task("logistics-mb", "logistics-bot")
# <- 同一个任务！租约过期后 Janus 重投了它。

# 现在带着调查结果 ACK（数据传给下游 Agent）：
client.ack_task(result.task.id, AckRequest(
    lease_id=result.lease.lease_id,
    agent_id="logistics-bot",
    result_ref='{"confirmed": true, "order": "ORD-789", "ordered": "red", "shipped": "blue"}',
))

第 4 步：扇出——三个并行分支

确认发错货后，Janus 协调三个并行工作流。每个分支用不同的路由方式：

# 分支 A：寄出正确商品（能力路由）
client.publish_task({"id": "ship-001", "source_agent": "logistics-bot",
    "target_type": "capability", "target_value": "reship",
    "envelope": {"task_id": "ship-001", "tenant_id": "acme",
                 "source_agent": "logistics-bot",
                 "target": {"type": "capability", "value": "reship"},
                 "payload": {"type": "reship", "content": "{\"order\": \"ORD-789\", \"correct\": \"red\"}"}},
})
# -> Janus 找到 shipping-bot（能力：reship）并路由到 shipping-mb

# 分支 B：取回错误商品（能力路由）
client.publish_task({"id": "ret-001", "source_agent": "logistics-bot",
    "target_type": "capability", "target_value": "retrieve_wrong",
    "envelope": {"task_id": "ret-001", "tenant_id": "acme",
                 "source_agent": "logistics-bot",
                 "target": {"type": "capability", "value": "retrieve_wrong"},
                 "payload": {"type": "retrieve", "content": "{\"order\": \"ORD-789\", \"wrong\": \"blue\"}"}},
})

# 分支 C：通知客户（能力路由到客服团队）
client.publish_task({"id": "notify-001", "source_agent": "logistics-bot",
    "target_type": "capability", "target_value": "notify",
    "envelope": {"task_id": "notify-001", "tenant_id": "acme",
                 "source_agent": "logistics-bot",
                 "target": {"type": "capability", "value": "notify"},
                 "payload": {"type": "notify", "content": "{\"message\": \"换货已启动\"}"}},
})

第 5 步：各 Agent 独立处理自己的分支

每个 Agent 独立拉取、处理、ACK 自己的任务，产出结果数据流向下游：

# shipping-bot：拉取 -> 处理 -> 带运单号 ACK
result = client.pull_task("shipping-mb", "shipping-bot")
client.ack_task(result.task.id, AckRequest(
    lease_id=result.lease.lease_id, agent_id="shipping-bot",
    result_ref='{"tracking": "SF789", "reshipped": true}',
))

# return-bot：拉取 -> 处理 -> 带取件信息 ACK
result = client.pull_task("return-mb", "return-bot")
client.ack_task(result.task.id, AckRequest(
    lease_id=result.lease.lease_id, agent_id="return-bot",
    result_ref='{"pickup": "PU123", "scheduled": true}',
))

# notify-bot：拉取 -> ACK（初始通知）
result = client.pull_task("notify-mb", "notify-bot")
client.ack_task(result.task.id, AckRequest(
    lease_id=result.lease.lease_id, agent_id="notify-bot",
))

第 6 步：数据汇合——合并结果

发货和回收都完成后，发布最终通知，合并两路结果——展示了 Agent 之间如何通过 Janus 传递和组合数据：

# 模式示意：上面的分支结果以各自任务的 result_ref 落盘；
# 真实应用通过 get_task_events("ship-001") / get_task_events("ret-001")
# （或你自己的结果存储）读取并合并。此处为简洁直接内联取值：
client.publish_task({"id": "notify-final", "source_agent": "shipping-bot",
    "target_type": "capability", "target_value": "notify",
    "envelope": {"task_id": "notify-final", "tenant_id": "acme",
                 "source_agent": "shipping-bot",
                 "target": {"type": "capability", "value": "notify"},
                 "payload": {"type": "notify",
                     "content": "{\"shipping\": {\"tracking\": \"SF789\"}, \"return\": {\"pickup\": \"PU123\"}, \"message\": \"红手机已发出(SF789)，蓝手机待取件(PU123)\"}"}},
})
这个示例展示的核心能力：这是一个完整的类生产工作流，覆盖了意图路由（LLM 驱动的自然语言→能力映射）、基于能力的路由（根据 Agent 能做什么来匹配）、同一管线中的多种路由类型、租约过期恢复（崩溃模拟）、并行分支执行，以及 Agent 之间的数据传递。同样的模式适用于客服工单处理、订单履约、理赔审核等任何需要多 Agent 协作并交换数据的工作流。
